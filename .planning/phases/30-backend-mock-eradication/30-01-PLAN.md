# Plan 30-01: Backend Mock Eradication & Strict API Constraints

**Phase:** 30 — Backend Mock Eradication & Strict API Constraints  
**Plan:** 30-01  
**Wave:** 1 | **Depends on:** []  
**Requirements:** PROD-01, PROD-03, PROD-04  

---

## Objective

Remove all synthetic alert simulation logic and offline mock fallback mechanisms from the FastAPI backend. Update the API endpoints to fail fast with standard HTTP 503 Service Unavailable errors when the upstream systems (MongoDB, Cisco DNA Center) are unreachable, enforcing strict production readiness.

---

## Must-Haves (Goal-Backward Verification)

<must_haves>
### Truths
- The backend never imports or relies on `simulate_data.py` (`PROD-01`).
- `get_alert_records()` throws an HTTP 503 error (FastAPI `HTTPException`) when MongoDB fails, rather than falling back to `load_simulated_alerts()` (`PROD-01`, `PROD-04`).
- `/api/alerts/simulate` endpoint is either removed or locked out completely (`PROD-01`).
- `/api/devices/{device_name}/telemetry` and `/api/devices/{device_name}/live-poll` throw HTTP 503 if live retrieval and cache retrieval both fail, instead of returning 200 OK with `source: offline` mock payload (`PROD-03`).
- API errors use proper FastAPI `HTTPException` so the client receives appropriate 503 HTTP status codes (`PROD-03`).

### Artifacts
- `dashboard/api.py` modified to remove `ALLOW_SIMULATED_DATA`, `load_simulated_alerts`, and replace fallback logic with `HTTPException`.
- `dashboard/device_service.py` modified to throw exceptions rather than returning default `offline` JSON templates when DNAC is unreachable.
- `tests/test_prod_hardening.py` updated to expect HTTP 503s instead of `source: simulated` when testing offline modes.
</must_haves>

---

## Step-by-Step Implementation

### Step 1: Remove Simulation Configuration and Functions
1. Open `dashboard/api.py`.
2. Import `HTTPException` from `fastapi`.
3. Delete the `ALLOW_SIMULATED_DATA` and `SIMULATED_FILE` environment variable checks and constants.
4. Delete the `load_simulated_alerts()` function completely.
5. Remove or comment out the `/api/alerts/simulate` route, or change it to always raise an `HTTPException(status_code=403, detail="Simulation disabled in production")`.

### Step 2: Enforce Strict MongoDB Checks
1. In `dashboard/api.py`, modify `get_alert_records()`:
   - If `mongo.get_collection("alert_results")` is None or throws an exception, catch it, log it, and `raise HTTPException(status_code=503, detail="Database unavailable")`.
   - Remove the fallback `return load_simulated_alerts()`. If no alerts exist in the DB, simply return `[]`.
2. In `/api/alerts`:
   - Remove the `if ALLOW_SIMULATED_DATA` source logic. `source` is always `"mongodb"`.

### Step 3: Enforce Strict DNAC Telemetry Constraints
1. In `dashboard/api.py`, update `get_device_telemetry()`:
   - In the `except Exception as e:` block, remove the return of the dummy offline payload.
   - Instead, log the error and `raise HTTPException(status_code=503, detail="Cisco DNA Center or telemetry cache unreachable")`.
2. Update `live_poll_device()` similarly to raise `HTTPException(status_code=503, detail="Cisco DNA Center unreachable")` on failure.

### Step 4: Verify Tests
1. Run `pytest tests/test_prod_hardening.py` or equivalent API tests.
2. Ensure that offline requests that used to expect `"source": "simulated"` or `"source": "offline"` now expect HTTP status 503. Update tests accordingly.

---

## Verification Criteria

1. Running `grep -r "simulate_data" dashboard/` returns nothing.
2. Invoking `/api/alerts` without a running MongoDB returns a 503 status code.
3. Invoking `/api/devices/{name}/telemetry` without DNAC and Cache returns a 503 status code.
