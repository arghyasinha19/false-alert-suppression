## Objective

Implement an authoritative tri-state connection machine (`connected` / `stale` / `offline`) with progressive retry backoff, freeze refresh timestamps on fetch failures, strictly validate API response payloads, propagate real connection status down to views and the SRE details drawer, clearly demarcate mock/demo datasets with top header chips and dismissible content banners, and provide manual "Reconnect API" controls and window focus re-checks.

### Task 1 — Implement Tri-State Connection Machine, Payload Validation & Polling Resiliency (`D-05`, `D-06`, `D-08`, `D-13`, `D-14`, `D-15`, `D-16`)

<read_first>
- `dashboard/src/App.jsx` (lines 35-115, 195-215, 240-255)
- `.planning/phases/19-critical-layout-status-fixes/19-UI-SPEC.md` §Copywriting Contract & Visual Hierarchy
- `.planning/phases/19-critical-layout-status-fixes/19-CONTEXT.md` §Decisions D-05, D-06, D-08, D-13, D-14, D-15, D-16
</read_first>

<action>
In `dashboard/src/App.jsx`:
1. Expand connection state from binary boolean to structured state:
   - `connectionState`: `{ status: 'connected' | 'stale' | 'offline', lastSuccessfulSync: Date | null, lastAttempt: Date | null, error: string | null, consecutiveFailures: number, retryCountdown: number }`.
2. Enhance `fetchData`:
   - Enforce strict payload validation (`D-08`): Verify both `Array.isArray(alertsRes?.alerts)` and `Array.isArray(devicesRes?.devices)`. If missing or not arrays, throw `new Error('Malformed API payload structure')`.
   - Handle empty responses (`D-15`): If both arrays are empty (`[]`), treat as valid `connected` state, updating data and setting `consecutiveFailures: 0`.
   - On success:
     - Set `status: 'connected'`, update `lastSuccessfulSync: new Date()`, reset `consecutiveFailures: 0`, and clear error.
   - On failure (`D-05`, `D-06`):
     - Increment `consecutiveFailures`.
     - If previously `connected` and `consecutiveFailures <= 2`, transition to `'stale'`.
     - If `consecutiveFailures >= 3` or never previously connected, transition to `'offline'`.
     - Freeze `lastSuccessfulSync` to the previous valid sync time (do not overwrite on failure).
     - Store error message (e.g., `error.message` or `Failed to fetch`).
3. Progressive Retry Backoff (`D-13`):
   - Calculate retry interval: 10s on failure 1, 20s on failure 2, 60s for 3+ failures. (Normal interval 30s when connected).
   - Manage polling timeout using `setTimeout` with adaptive delay rather than fixed `setInterval`.
4. Triggers & Controls (`D-14`):
   - Add window focus listener (`window.addEventListener('focus', () => { if (connectionState.status !== 'connected') fetchData(); })`).
   - Add manual "Reconnect API" button in header actions and sidebar status row.
5. Diagnostic Tooltip (`D-16`):
   - Populate badge tooltip / title with endpoint URL (`${API_BASE}/api/alerts`), last attempted timestamp, error reason, and next retry countdown.
</action>

<acceptance_criteria>
- Connection status models `connected` ("Live"), `stale` ("Stale"), and `offline` ("Offline").
- `lastSuccessfulSync` freezes on failure and does not update when fetches reject.
- Malformed payloads without array properties throw errors and trigger error states.
- Polling uses progressive backoff (10s -> 20s -> 60s) on failures.
- Window focus listener triggers immediate reconnect checks.
</acceptance_criteria>
